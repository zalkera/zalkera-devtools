# 설계 메모 — 사이트 선택 뒤의 흐름(site-choice flow)

> 실사용 신고: 사이트가 선택되고 폴더가 열린 상태에서 다른 사이트로 전환하려고 「사이트」를
> 누르면 「그 사이트 소스 다운로드」 하나만 나온다. 빈 폴더를 지정해 zip 을 올리는 길, 기존
> 소스 디렉터리를 다시 붙는 길, 그냥 취소하는 길이 화면에 없다.

본 메모는 `DESIGN-site-folder-binding.md` 를 정본으로 두고 그 위에 선다 — 소속 정책(표식 정본·
명시 재연결·쓰기 범위 `none`)은 그대로이고, 여기서 고치는 것은 **사이트를 고른 뒤 사람에게
무엇을 내는가**다.

**개정 지점**: 본 메모 §4 가 `DESIGN-site-folder-binding.md` **§4.4 의 「제안 흐름」 부분을 대체
개정**한다(레지스트리·확증·`ACCOUNT_SCOPED` 등재는 그대로 유효). 같은 문서 §9 표의
`decideSiteChoice` 행은 본 메모 §8 로 보강되고, §10 쟁점 1~5 는 건드리지 않으며 본 메모 §9 가
쟁점을 추가한다. §4.3(쓰기 범위)·§4.5(명시 재연결)·§4.6(발행 결정화)·§3(신뢰 서열)은 **변경
없음**이다.

## 0. 결론 요약

**정책 한 줄**: 소속이 다른 폴더에서 사이트를 고르면, 사라지는 알림 한 장 대신 **선택지가 나열된
QuickPick 한 장**을 낸다 — 열기·다운로드·로컬본 직접 고르기·zip 으로 시작을 순서대로 내고,
Esc 가 곧 취소다(아무것도 적히지 않는 것은 `decideTenantScope` 의 `none` 이 이미 담보한다).
받을 판이 없는 사이트(P0)에는 다운로드를 **내지 않는다** — 제안 표면은 실패를 약속하지 않는다.

| 항목 | 판정 | 형상 |
|---|---|---|
| ① 오너 시나리오: 빈 폴더에 zip/소스 넣기 | **채택(자리 이동)** | 사이트 선택이 아니라 **받기·zip 풀기의 대상 기본값**이 자리다 — 열어 둔 빈 폴더를 첫 제안으로(`decideFetchTargetPlan`, §4.5). 사이트 선택 2단에서는 「받은 zip 으로 시작」 항목이 그 길로 잇는다 |
| ② 오너 시나리오: 기존 소스 디렉터리 재연결 | **갈라서 채택** | ⑴ 로컬본을 **찾아 여는 것**은 신설 「로컬본 폴더 직접 고르기」(확증 규칙 동반, §4.4). ⑵ 이 폴더의 **소속을 바꾸는 것**(재연결)은 사이트 선택에 넣지 않는다 — 정본 §4.5 의 「사이트에 연결」 전용 유지(가장 위험한 동사를 가장 흔한 흐름의 한 클릭 거리에 두지 않는다) |
| ③ 오너 시나리오: 취소하고 닫기 | **채택(형태의 부수 효과)** | QuickPick 의 Esc 가 취소다. 무기록 보장은 기존 `none` 판정 그대로 |
| ④ P0×W4 결함(누르면 반드시 실패하는 다운로드 단추) | **채택(논블로킹 조회)** | 2단을 **연 채** 고른 사이트의 판 목록을 조회해, 받을 판이 없다고 확인되면 다운로드 항목을 빼고 이유를 말한다. 조회가 **실패**하면 항목이 남는다 — 모르는 것으로는 막지 않는다(§4.3). 조회 왕복 동안의 노출 창은 §6.2 |
| ⑤ 알림 → QuickPick 전환 | **채택(elsewhere 한정)** | switched·adopted 는 토스트 유지 — 흔한 경로에 마찰을 더하지 않는다(§3.1) |
| ⑥ 입양(W2) 알림에 되돌림 단추 | **채택** | 「다시 연결」 단추 하나(`zalkera.site.link`). 입양 자체의 사전 확인은 기각 — 표식 부재로 막지 않는다는 이행 원칙 그대로(§3.2 관측 7·8) |
| ⑦ 로그아웃 뒤 K0 퇴행 | **부분 채택** | 소속 있는 폴더를 연 창이 레지스트리에 재등재한다(§4.7). 로그아웃 시 레지스트리 보존은 기각 — `ACCOUNT_SCOPED` 근거 그대로 |
| ⑧ 새 창/이 창 항상 묻기 · 최근순 정렬 · 다사이트 발행 동사 | **기각·이연** | §3.2 관측 3·6·4. 다사이트 발행(프랜차이즈)은 재연결과 다른 동사가 맞고, 그래서 이 흐름에 욱여넣지 않고 별도 설계로 이연(§9) |

- **판정은 전부 core 순수 함수로**: `decideSiteChoice`(4갈래로 확장)·신설 `elsewhereOptions`·
  `decidePickedFolder`·`decideFetchTargetPlan`(§4.1). 확장은 그리기만 한다.
- **사이드바 변경 없음** — 묶음·항목 수 그대로(오너 확정 불변식). 게이트(`whyBlocked`) 문면·단추도
  변경 없음.
- **`@zalkera/client`·examples 변경: 불필요**(§7) — devtools 단독, 서버 계약 추가 없음.
- **판 등급: minor**(0.10.0 기준 다음은 0.11.0). 근거 §7.
- 미해결 쟁점의 처분: §9.
- **구현 심의를 반영해 개정했다**: §4.3(논블로킹 조회·4초 선), §4.1·§4.2(P0a/P0b 분리),
  §4.5(zip 은 `here` 갈래만), §4.8 삭제(1단 정렬 기각), §6(심링크 부모·항목 라벨 등재),
  §7(근거 정정), §9(처분). 항목별 판정과 잔여는 §10. 다중 사용자 덮어쓰기 축은 별도 메모
  `DESIGN-concurrent-upload.md` 로 갈랐다.

## 1. 현 상태 (코드 사실)

(본 절은 설계 착수 시점의 형상이다 — 구현이 반영된 형상은 §4, 그 심의는 §10.)

사이트 선택의 흐름은 `extension.ts` 의 `chooseSite` → `chooseTenant(true)`(QuickPick) →
`saveTenant`(core `decideTenantScope` 로 범위 판정) → `decideSiteChoice` → 갈래별 산출이다.

| 갈래 | 지금 산출 | 자리 |
|---|---|---|
| `switched` | 토스트 `사이트: y` · 로그 한 줄 | `chooseSite` |
| `adopted` | 토스트 `say.folderAdopted` — 되돌리는 길은 문면·단추 어디에도 없다 | `chooseSite` |
| `elsewhere` | **비-모달 알림 + 단추 하나** — `offer` 가 `open` 이면 「그 사이트 폴더 열기」, `fetch` 면 「그 사이트 소스 다운로드」 | `offerFolderElsewhere` |

- `offer` 는 `decideSiteChoice` 의 `knownFolderConfirmed`(레지스트리 확증) 하나로 갈린다 —
  둘 중 **하나만** 나오고, 나머지 길(직접 고르기·zip·취소)은 화면에 없다.
  재현: `grep -n "offer: input.knownFolderConfirmed" packages/core/src/siteBinding.ts`
- **P0×W4·K0 결함**: 「그 사이트 소스 다운로드」 → `openSite(captureTenant(picked))` →
  `api.listRevisions()` → `pickRevision` 이 READY 판이 없으면 `null` → `noRevisionError` 가
  던진다. 갓 만든 테넌트로 전환하는 사람이 정확히 이 칸에 오고, 단추는 누르면 반드시 실패한다.
  오류 문면 자체는 두 갈래(판 0건 / READY 0건)로 정직하지만, **제안한 단추가 실패로 끝나는 형상**은
  커밋 bd0bdc8 이 걷어낸 「지금 전환」과 같다.
  재현: `grep -n "noRevisionError" packages/core/src/fetchTarget.ts packages/vscode/src/extension.ts`
- 받기 대상 제안(`chooseFetchTarget`)은 열린 폴더의 **옆에 새 폴더**를 제안하거나 대화상자로
  보낸다. 열린 폴더가 **비어 있어도** 그 폴더 자체는 제안되지 않는다 — 대화상자에서 손으로
  고르면 받아진다(`fetchSiteSource` 의 빈 폴더 강제는 `isReceivable` 이고, 도구가 만든 `.vscode`
  는 무시한다 — `emptyDir.ts`). 「zip 으로 시작」의 대상 대화상자에는 기본값 제안이 없다.
- `chooseTenant` QuickPick 은 항목 `detail` 에 확증된 로컬본 경로를 이미 보여 준다.
  재현: `grep -n "confirmedFolderFor(t.code)" packages/vscode/src/extension.ts`
- 레지스트리(`zalkera.folderRegistry`)는 받기·재연결·복귀 성공 시에만 적히고, 로그아웃이
  통째로 버린다(`clearFolderRegistry`, `ACCOUNT_SCOPED` 집행). 표식이 디스크에 남아 있어도
  재로그인 뒤에는 K0 으로 돌아간다.
- `openSiteFolder` 는 미리보기가 돌거나 미저장 편집기가 있을 때만 새 창/이 창을 묻고, 평시에는
  이 창을 덮는다.

이 산출들은 결함이 아니라 정본 §4.4 가 그렇게 설계한 것이다 — 고치는 대상은 그 절이다.

## 2. 사례 매트릭스 판정

발주자의 축 설정을 검증한다. 뼈대는 옳고, 세 군데를 정정·보강한다.

### 2.1 축 W — 「표식 없음」이 아니라 「소속(binding) 없음」으로 잰다

판정 정본은 `folderBinding`(표식 > 워크스페이스 링크)이다. 「표식 없음·링크 있음」(구판 받기,
표식 쓰기 실패 잔재)은 W2 가 아니라 링크가 가리키는 사이트의 W3/W4 로 행동한다. 축을 표식으로
정의하면 이 폴더들이 표에서 사라진다. 정정한 축:

- **W0** 폴더 안 열림
- **W1a** 폴더 열림 · 소스 아님 · **비어 있음**(`meaningfulEntries` 기준 — 오너 시나리오 ①의 자리)
- **W1b** 폴더 열림 · 소스 아님 · 비어 있지 않음(무관한 프로젝트·바탕화면 등)
- **W2** 소스 폴더 · **binding 없음**(표식도 링크도 없음 — zip 으로 푼 상태가 여기)
- **W3** 소스 폴더 · binding == 고른 사이트
- **W4** 소스 폴더 · binding == 다른 사이트

W1 의 분할이 필요한 이유: 받기·zip 풀기의 대상으로 쓸 수 있는 것은 W1a 뿐이고(빈 폴더 강제),
W1b 에 옆 폴더 제안(`suggestSibling`)을 내는 지금 동작은 이름부터 무의미하다(`바탕화면-v13`).

### 2.2 축 P — 셋으로 가른다

`pickRevision`·`noRevisionError` 가 이미 두 「없음」을 가른다: **P0a** 판 0건(신규 테넌트) /
**P0b** 판은 있으나 READY 0건(전부 BUILDING·FAILED). 그리고 P 는 서버 사실이라 조회가 실패할 수
있다 — **P?**(모름) 칸이 실재하고, 이 칸의 규율은 표식과 같다: **모르는 것으로는 막지 않는다.**
P0a·P0b 모두 다운로드가 빠지는 것은 같지만, zip 승격(§4.1)은 P0a 만 받고 이유 문면도 갈린다 —
빌드가 도는 사이트의 사용자를 새 시작으로 보내면 오진이다.

### 2.3 축 K — 옳다. 단서 하나

K1 은 「레지스트리가 기억」이 아니라 「**확증까지 통과**」다(`confirmedFolderFor` — 실재 + 소속
일치). 이미 코드가 그렇게 한다. 신설 「직접 고르기」(§4.4)가 K0 의 막다른 길을 없애므로, K 는
선택지 유무가 아니라 **첫 항목이 무엇인가**만 가른다.

### 2.4 추가 축 하나, 비축 판정 셋

- **T 축(창의 유효 사이트 == 고른 사이트인가)** — 보강. 지금 `switched` 는 「바꿨다」와 「이미
  그 사이트였다」를 한 문장으로 뭉친다(무동작인데 뭔가 한 것처럼 보이는 W3 관측의 뿌리).
  T 는 선택지를 바꾸지 않고 **문면만** 가른다(§4.1 의 `unchanged`).
- **미리보기 실행 중 · 미저장 편집** — 축이 아니다. 폴더를 **여는 잎**에서만 갈리고
  `openSiteFolder` 가 이미 그 분기를 갖는다(새 창 기본 제안). 매트릭스에 올리면 칸이 배가되는데
  산출은 같다.
- **멀티루트 워크스페이스** — 축이 아니다. 정본 §2 가 멀티루트를 기각했고 `workspaceDir()` 은
  첫 루트만 본다. 이 흐름도 그 전제를 그대로 따른다(첫 루트 기준 판정 — 못 가르는 것으로 §6.3 에
  적는다).
- **원격 SSH** — 축이 아니다. 이 확장은 파일을 만지므로 워크스페이스 쪽에서 돌고, 레지스트리
  (`globalState`)와 그것이 가리키는 경로가 같은 확장 호스트에 산다는 전제가 성립한다. 이 전제는
  구현 단계에서 원격 창 하나로 확인한다(§9).

## 3. 정책과 대안 검토

### 3.1 화면 형태 — elsewhere 는 QuickPick 2단, 나머지는 토스트 유지

**채택**: `elsewhere` 갈래에서만, 사이트 QuickPick(1단)에 이어 **선택지 QuickPick(2단)** 을 낸다.

근거:

- **알림은 이 일에 구조적으로 좁다.** 비-모달 알림은 단추 두셋이 실용 한계이고 자동으로 사라지며,
  본문은 한 줄로 잘린다. 지금 산출이 「단추 하나」인 것은 게으름이 아니라 이 형태의 귀결이다 —
  선택지가 넷이면 그릇을 바꿔야 한다.
- **QuickPick 은 이 확장의 기존 어법이다.** 1단(사이트 고르기)이 이미 QuickPick 이라, 2단은 같은
  화면이 한 번 더 뜨는 것으로 읽힌다. 항목마다 `detail` 로 경로·결과를 붙일 수 있고, Esc 가
  취소라는 관습이 서 있으며, 떠 있는 동안 사라지지 않는다.
- **취소의 정직성**: 관측 9(「골랐는데 아무 일도 안 일어난다」)는 2단이 떠 있는 것 자체로 해소된다
  — 화면이 「아직 끝나지 않았다」를 말한다. Esc 로 닫으면 창은 이전 상태 그대로다(`none` 판정이
  이미 무기록을 담보 — 새 보장이 아니라 기존 보장의 가시화다).

기각한 대안:

- **모달 대화상자** — 기각. 모달은 이 레포에서 파괴적 동의(재연결·발행) 전용이다. 사이트 전환은
  일상 동작이라 모달로 막아 세우면 형식이 위험도를 거짓말한다.
- **1단 QuickPick 항목에 단추(QuickPickItemButtons) 부착** — 기각. 아이콘 단추는 발견성이
  없고(호버해야 보인다), 항목당 동사 여러 개를 싣는 표면은 오클릭 표면이기도 하다.
- **알림 유지 + 단추 증설** — 기각. 셋을 넘기면 렌더가 「…」 뒤로 접고, 자동 소멸은 그대로다.
- **switched·adopted 까지 2단으로** — 기각. 사이트 전환의 대다수는 W0·W3(그냥 창의 대상 바꾸기)
  이고, 거기에 화면을 하나 더 끼우면 흔한 경로가 느려진다. 결정할 것이 없는 곳에 결정 화면을
  내지 않는다.

### 3.2 관측 10건의 채택·기각

| # | 관측 | 판정 | 사유 |
|---|---|---|---|
| 1 | 「사이트」가 두 동사(창의 대상 / 편집할 소스)를 뭉쳤다 | **진단 채택 · UI 분리 기각** | 진단이 이 설계의 뼈대다 — `switched`(창의 대상)와 2단(소스로 가는 길)이 그 분리다. 사이드바 항목을 둘로 쪼개는 것은 기각: 항목 증식이고, 「대상만 바꾸기」와 「소스로 가기」를 사람이 미리 구분해 누르게 하는 것은 그 뭉침을 사용자에게 떠넘기는 것이다 |
| 2 | 알림이라 단추를 못 늘린다 → QuickPick 2단? | **채택(elsewhere 한정)** | §3.1 |
| 3 | 새 창/이 창을 평시에도 물어야 — 대행사는 두 창이 기본 | **기각** | 잃을 것이 없을 때 이 창을 덮는 현행이 옳다 — 폴더는 디스크에 그대로고 레지스트리로 되돌아온다. 대행사가 두 사이트를 **동시에** 작업 중이면 그 창에 미리보기·미저장이 있고, 바로 그때 `openSiteFolder` 가 새 창을 기본으로 묻는다. 평시 모달은 백 번의 전환에 백 번의 마찰이다 |
| 4 | 한 소스 → 여러 사이트(프랜차이즈)는 재연결과 다른 동사인가 | **판단 채택 · 설계 이연** | 다른 동사가 맞다 — 소속의 이동이 아니라 **발행 대상의 복수화**다. 그래서 재연결로도, 사이트 선택으로도 표현하지 않고 별도 설계로 이연한다(§9). 지금 우회로(재연결 왕복)는 동의 모달 두 번을 지나는 정직한 경로로 남는다 |
| 5 | 로그아웃이 레지스트리를 버려 K0 퇴행 | **부분 채택** | 재등재는 §4.7. 로그아웃 시 보존은 기각 — 앞 계정의 사이트 코드·경로가 다음 계정의 제안 표면에 남는 것이 `ACCOUNT_SCOPED` 등재의 이유였고, 그 판정을 뒤집을 새 사실이 없다 |
| 6 | 사이트 QuickPick 에 최근순 정렬·로컬본 표시가 없다 | **표시 채택 · 정렬 기각** | 로컬본 표시는 **이미 있다**(`detail` 에 확증 경로 — §1 재현 명령)이고, 「지금 작업 중」 표시가 더해진다. 정렬은 기각 — `detail` 이 같은 정보를 이미 말해 순서를 바꿔 얻는 것이 없고, 콘솔의 사이트 목록 순서와 편집기가 갈린다(§9 쟁점 6). 최근순도 기각 — 레지스트리에 시각 칸을 더하는 판올림 대비 편익이 없다. 수십 개면 QuickPick 의 타자 필터가 이미 그 일을 한다 |
| 7 | zip 폴더가 표식이 없어 오선택이 W2 입양으로 굳는다 | **방지 기각 · 완화 채택** | 입양에 사전 확인을 달면 표식 없는 구판 폴더 전원이 물음을 맞는다 — 「표식의 부재로는 막지 않는다」 위반이다. 완화는 관측 8 의 단추와 발행 확인 모달(기존 최종 방어선) |
| 8 | 입양을 되돌리는 길이 알림에 없다 | **채택** | §4.6 — 단추 「다시 연결」 하나 |
| 9 | 취소가 늦다 | **부분 채택** | elsewhere 는 2단이 해소. switched·adopted 의 「고르면 적힌다」는 유지 — 그 기록은 저위험(자기 창의 대상)이고, 고르기 전 확인 단계는 흔한 경로의 마찰이다. 잘못 골랐으면 같은 화면에서 다시 고르는 것이 실행 취소다 |
| 10 | 없는 것은 「열어 둔 빈 폴더를 그대로 쓰는 길」 | **채택** | §4.5 — 자리는 사이트 선택이 아니라 받기·zip 풀기의 대상 판정이다. 사이트 선택에 실으면 W1a 전환마다 서버 조회·제안이 붙는데, 빈 폴더를 열어 둔 사람이 다음에 누르는 것은 어차피 「소스 다운로드」·「zip 으로 시작」이다 — 그 자리에서 기본값이 맞는 것이 정석이다 |

P0 칸에서 「예제 zip 다운로드」까지 2단에 싣는 안도 검토했다 — **기각**. 항목 증식이고, 그 길은
`noRevisionError` 문면과 사이드바 상시 항목(내려받기)이 이미 안내한다.

## 4. 형상 설계

### 4.1 core 판정부 — `siteBinding.ts` 의 새 형상

지금 셋(`switched`·`adopted`·`elsewhere{offer}`)으로 부족한 것: ⑴ `elsewhere` 가 단일 `offer` 로
접혀 선택지 목록·순서를 표현할 수 없다 ⑵ 「이미 그 사이트」와 「바꿨다」가 한 칸이다 ⑶ 직접 고른
폴더의 처분과 받기 대상 기본값이 확장 안 조건문으로 갈 자리가 없다.

```ts
/** 사이트를 고른 뒤 화면이 할 일. */
export type SiteChoice =
    | {kind: "unchanged"}   // 이미 그 사이트로 작업 중 — 재확인만 말한다
    | {kind: "switched"}    // 창의 대상이 실제로 바뀌었다(복원 포함)
    | {kind: "adopted"}     // 소속 없던 소스 폴더가 입양됐다
    | {kind: "elsewhere"};  // 소속이 다르다 — 선택지는 elsewhereOptions 가 정한다

export function decideSiteChoice(input: {
    picked: string;
    binding: string | null;
    siteFolderOpen: boolean;
    current: string;        // 고르기 전의 유효 사이트(tenantCode) — unchanged 판정용
}): SiteChoice;

/** elsewhere 2단의 항목. **배열 순서가 곧 화면 순서이자 권고다.** */
export type ElsewhereOption =
    | {kind: "open"; dir: string}   // 확증된 로컬본 열기
    | {kind: "fetch"}               // 새 빈 폴더로 다운로드
    | {kind: "pick-folder"}         // 로컬본 폴더 직접 고르기
    | {kind: "import-zip"};         // 받은 zip 으로 시작

export function elsewhereOptions(input: {
    /** 확증까지 마친 레지스트리 값. 기억만 있는 값을 넣으면 안 된다. */
    confirmedDir: string | null;
    /**
     * 고른 사이트의 판 조회 결과. 「없다」는 두 사유로 가른다 — `no-revision`(판 0건, P0a)·
     * `no-ready`(READY 0건, P0b). `unknown`(조회 실패)은 막지 않는다.
     */
    fetchable: "yes" | "no-revision" | "no-ready" | "unknown";
}): {options: ElsewhereOption[]; note: "no-revision" | "no-ready" | null};

/** 직접 고른 폴더의 처분. */
export type PickedFolderPlan =
    | {kind: "open"}                    // binding == 고른 사이트 — 링크를 소속에 맞추고 연다
    | {kind: "link-consent"}            // binding 없음 — 동의 후 링크+표식을 쓰고 연다
    | {kind: "refuse"; bound: string};  // 다른 사이트의 소스 — 열지 않는다

export function decidePickedFolder(binding: string | null, chosen: string): PickedFolderPlan;

/** 받기·zip 풀기의 대상 제안. 두 소비처(받기·zip 으로 시작)가 같은 판정을 지난다. */
export type FetchTargetPlan =
    | {kind: "here"; dir: string}         // 열어 둔 빈 폴더 — 첫 제안
    | {kind: "sibling"}                   // 소스 폴더 옆 새 이름 — 현행 유지
    | {kind: "pick-only"};                // 대화상자로만(W1b 등)

export function decideFetchTargetPlan(input: {
    openDir: string | null;
    openDirReceivable: boolean;   // isReceivable(openDir) — 확장이 재서 넘긴다
    siteFolderOpen: boolean;
}): FetchTargetPlan;
```

- `unchanged`: `current === picked` 이고 소속이 그것과 어긋나지 않을 때. 어긋난 창(표식 x·링크
  잔재로 유효 사이트가 y)에서 x 를 다시 고르면 `switched` 다 — 복원이 실제로 일어나므로
  「바꿨습니다」가 참이다.
- `elsewhereOptions` 순서: `[open?, fetch?, pick-folder, import-zip]`. **P0a(`no-revision`)에서만
  `import-zip` 을 `pick-folder` 앞으로** 올린다 — 판 없는 사이트로 전환하는 사람의 흔한 형상이
  zip 입고(신규 테넌트 온보딩)다. P0b(`no-ready`)는 승격하지 않는다 — 잠시 기다리면 될 사람을
  새 시작으로 보내지 않는다. `no-revision`·`no-ready` 면 `fetch` 가 빠지고 그 사유가 `note` 에
  실린다. `"unknown"` 이면 `fetch` 를 남긴다 — 눌러서 실패하면 `noRevisionError` 가 정직하게
  진단한다.
- 함수 넷 모두 파일시스템·`vscode`·네트워크를 모른다. 확장이 사실(확증 폴더·판 조회 결과·
  빈 폴더 여부)을 재서 넘긴다.

### 4.2 칸별 산출 — 선택지 목록과 순서·기본값

| 칸 | 산출 | 비고 |
|---|---|---|
| W0 · T같음 | `unchanged` 토스트 | 문면: `이미 「y」 로 작업 중입니다.` |
| W0 · T다름 | `switched` 토스트(현행 `사이트: y`) | 전역 쓰기(현행). 추가 안내 없음 — 사이드바 상시 묶음이 다음 할 일이다 |
| W1a(빈 폴더) | `switched` 토스트 | 전환 자체는 W0 과 같다. 빈 폴더 활용은 §4.5 의 대상 기본값이 맡는다 |
| W1b | `switched` 토스트 | 같음 |
| W2 | `adopted` 토스트 + 단추 「다시 연결」 | §4.6 |

| W3 · T다름 | `switched` 토스트 | 어긋난 링크의 복원 경로(정본 §4.3 셋째 행) — 실제로 바뀌므로 「바꿨습니다」류가 참 |
| W4 · K1 · P1 | 2단: **열기** → 다운로드 → 직접 고르기 → zip 으로 시작 | 첫 항목이 기본값(포커스) |
| W4 · K0 · P1 | 2단: **다운로드** → 직접 고르기 → zip 으로 시작 | |

| W4 · K1 · P0b | 2단: **열기** → 직접 고르기 → zip 으로 시작 + 이유 한 줄 | 다운로드 없음 · zip 승격도 없음 |
| W4 · K0 · P0a | 2단: **zip 으로 시작** → 직접 고르기 + 이유 한 줄 | 신규 테넌트 첫 접속이 이 칸 |
| W4 · K0 · P0b | 2단: **직접 고르기** → zip 으로 시작 + 이유 한 줄 | 잠시 뒤 받으면 될 사람이다 |
| W4 · P? | P1 과 같은 구성 | 조회 실패로는 막지 않는다 |

P0 칸의 구성은 조회가 돌아온 **뒤**의 형상이다 — 2단은 조회를 기다리지 않고 P1 구성으로 먼저
그려지고, 조회가 빼라고 말할 때만 다시 그려진다(§4.3). 그 왕복 동안의 노출 창은 §6.2 에 적는다.

취소(Esc)는 모든 칸에서 무기록이다 — W4 는 `none` 판정이, 2단은 아무 동작도 시작하지 않은
상태가 담보한다.

### 4.3 elsewhere 2단 화면

- 진입: `chooseSite` 가 `elsewhere` 를 받으면 ⑴ 고른 사이트를 `captureTenant(picked)` 로 잡고
  (기존 `offerFolderElsewhere` 의 캡처 자리를 승계 — 캡처 지점 수 불변) ⑵ `confirmedFolderFor
  (picked)` 를 확증하고 ⑶ `elsewhereOptions({fetchable: "unknown"})` 구성으로 **바로 그리고**
  ⑷ 그 캡처로 묶은 API 의 `listRevisions` 가 `no-revision`·`no-ready` 를 말할 때만 항목과
  placeholder 를 다시 그린다.
- **조회는 화면을 막지 않는다.** 조회를 앞세워 벌 수 있는 것은 「판 없는 사이트에서 받기 한 줄을
  뺄 기회」뿐인데(시한을 넘기면 어차피 그 줄이 남는다), 대가로 흔한 칸까지 빈 목록을 보게 된다.
  실패·시한 초과는 `"unknown"` — 그대로 둔다. 늦게 온 답은 `FETCHABLE_PROBE_MS`(4초) 선에서
  버린다 — 화면을 막지 않으므로 이 상수는 시한이 아니라 **낡은 답으로 화면을 다시 그리지 않는
  선**이고, 제어 평면 상한(30초)을 그대로 물려받으면 그만큼 타이머가 살아 있게 된다. 이미
  고르거나 닫힌 화면은 다시 만지지 않는다. P0 에서 받기 줄이 왕복 시간만큼 보이는 창은 §6.2 에
  적는다.
- 문면(전부 `tenantScope.ts` 의 `say` 에 추가 — 소독 정본 자리. QuickPick 제목은 링크를 렌더하지
  않지만 제어문자·초장문 차단은 같은 잣대로 받는다):
  - 제목: `「y」 작업은 다른 폴더에서 합니다 — 이 폴더는 「x」 에 연결돼 있습니다`(「소스입니다」로
    단정하지 않는다 — 소속은 있는데 소스가 아닌 폴더도 이 화면에 온다)
  - P0a placeholder: `「y」 에는 아직 올린 소스가 없습니다 — zip 으로 시작하실 수 있습니다.` /
    P0b: `「y」 의 판이 아직 만들어지는 중이거나 실패했습니다 — 「버전 이력」에서 확인하실 수
    있습니다.`(`noRevisionError` 의 두 갈래와 같은 진단)
- 항목 라벨은 리터럴, 경로·판 번호는 `detail` 로:
  - `그 사이트 폴더 열기` — detail: 확증된 경로. 실행: 누른 시점 재확증(현행 규율) 후
    `openSiteFolder`(미리보기·미저장 시 새 창 제안 — 현행 잎 유지).
  - `그 사이트 소스 다운로드` — detail: `새 빈 폴더에 받습니다 — 지금 폴더는 그대로 둡니다`.
    실행: `openSite(pinned)` — 가드는 그 안쪽 해제 구간이 잡는다(`whileExtracting`).
  - `로컬본 폴더 직접 고르기…` — §4.4.
  - `받은 zip 으로 시작…` — 실행: `zalkera.site.importZip` 호출(요건 `signedIn` 뿐이라 이
    상태에서 막히지 않는다). 대상 기본값은 §4.5 가 정한다.
- 기존 `say.pickedElsewhere` 알림과 `offerFolderElsewhere` 는 이 화면으로 대체된다.

### 4.4 「로컬본 폴더 직접 고르기」 — 확증을 지나는 열기

대화상자(제목: `「y」 의 소스 폴더 고르기`)로 폴더를 받아 `folderBinding` 을 읽고
`decidePickedFolder` 로 처분한다:

- **`open`**(binding == y): `linkFolderToTenant(dir, y)` 로 링크를 소속에 맞추고(표식이 진실 —
  `useFolderSite` 와 같은 복원 의미라 동의 없음) `rememberFolder` 후 `openSiteFolder`.
- **`link-consent`**(binding 없음): **모달 동의** — `고르신 폴더를 「y」 에 연결할까요? 연결하면
  이 폴더의 소스가 「y」 사이트로 올라가게 됩니다.` 확인 시 링크와 `linked` 표식을 **같이** 쓰고
  (「사이트에 연결」과 같은 쌍 — 「어긋남은 사고다」 유지), 레지스트리 갱신 후 연다. 취소 시
  **열지 않는다** — 연결 없이 열면 새 창의 유효 사이트가 전역 잔값이 되어, 정본 §4.3 넷째 행이
  막은 바로 그 형상(무소속 폴더 + 잘못된 유효 사이트)을 우리 제안이 만들게 된다.
- **`refuse`**(binding == z ≠ y): 열지 않고 말한다 — `고르신 폴더는 「z」 의 소스입니다 —
  「y」 폴더가 아니라서 열지 않았습니다.` 재활용된 경로를 「그 사이트 폴더」로 내주지 않는다는
  레지스트리 확증과 같은 잣대다.

이 동사는 재연결이 아니다 — 열려 있지도 않은 폴더의 소속을 사이트 선택이 바꾸는 일은 없고,
`link-consent` 는 소속이 **없는** 폴더에 소속을 처음 주는 것(입양의 명시·동의판)이다.

### 4.5 받기·zip 풀기의 대상 기본값 — 열어 둔 빈 폴더가 첫 제안

`chooseFetchTarget`(받기)과 「zip 으로 시작」의 대상 선택이 같은 판정(`decideFetchTargetPlan`)을
지난다:

- **`here`**(열린 폴더가 소스 아님 + `isReceivable`): 첫 제안이 `이 폴더에 받기`(zip 은 `이
  폴더에 풀기`) + `다른 폴더 고르기…`. 빈 폴더 강제는 지금처럼 실행 시점에 `fetchSiteSource`·
  `importZipInto` 가 다시 잰다 — 제안과 강제를 한 판정으로 합치지 않는다(그 사이 파일이 생길 수
  있다).
- **`sibling`**(소스 폴더 열림): 현행 유지 — 옆에 `이름-v판` 제안.
- **`pick-only`**(W1b 등): 대화상자로만. W1b 에 옆 폴더 제안을 내는 현행의 무의미한 이름 제안이
  같이 사라진다.
- **zip 소비처는 `here` 갈래만 산다.** `sibling` 의 옆 이름 제안(`이름-v판`)은 판 번호를 아는
  받기 전용이라, zip 은 `sibling`·`pick-only` 에서 대화상자로 간다 — 소스 폴더 옆에 뜻 없는
  이름을 지어 주지 않는다.
- **받기 완료 문면의 `into-open` 갈래가 필수다.** 「새 폴더로 받았습니다. 지금 폴더는 바뀌지
  않았습니다」는 대상이 열린 폴더 자신이면 두 문장 다 거짓이 된다. 세 번째 갈래를 더한다:
  `「y」 버전 N 을 지금 폴더에 풀었습니다. 이 폴더가 그 사이트의 소스가 됐습니다.`(열기 단추
  불요 — 이미 열려 있다). `openSite` 의 「받은 폴더가 지금 열린 폴더일 수 있다」 갱신 경로는
  이미 있다.

### 4.6 입양(adopted) 알림의 되돌림 단추

`say.folderAdopted` 토스트에 단추 「다시 연결」(리터럴, `zalkera.site.link`)을 단다. 누르면
사이트 목록이 다시 나오고, 다른 사이트를 고르면 `needsRelinkConsent` 의 동의 모달이 선다 —
새 경로가 아니라 기존 재연결 경로로 보내는 손잡이다. 입양 자체를 묻는 사전 확인은 달지 않는다
(§3.2 관측 7).

### 4.7 레지스트리 재등재 — 여는 제스처가 기억을 되살린다

확장 활성화 시(그리고 로그인 직후 갱신 시) 열린 폴더의 `folderBinding` 이 있으면
`rememberFolder(binding, dir)` 로 재등재한다. 값이 같으면 쓰지 않는다(잦은 갱신 경로에 쓰기를
얹지 않는다). 로그아웃의 `clearFolderRegistry` 는 그대로다 — 재등재는 **그 폴더를 연 사람의
제스처**에서 나오고, 노출 표면(1단 `detail`·2단 열기)은 그 계정이 열거할 수 있는 사이트로 이미
한정되므로 `ACCOUNT_SCOPED` 의 근거를 건드리지 않는다.

## 5. 이행

- **전부 가산이다.** 표식 형식(format 1·2)·워크스페이스 링크·레지스트리 키·서버 API 계약에
  변화가 없다. 구판 확장과 새 확장이 같은 폴더를 오가도 판독·게이트가 그대로 선다.

- 사이드바·게이트(`whyBlocked`)·상태바는 변경 없음. 게이트의 대안 단추 「그 사이트 소스

  사실(P)을 모르고, 그 명령의 오류 문면이 두 갈래로 정직하다. **제안 표면(2단)은 미리 알고
  거르고, 상시 진입점은 눌렀을 때 정확히 진단한다** — bd0bdc8 교훈의 적용 경계를 이렇게 긋는다.

## 6. 보안 판정

### 6.1 막는 것 · 지키는 것

- 교차 업로드 방어의 기존 층(표식 정본·`none` 무기록·게이트·발행 모달)은 전부 그대로다 — 이
  설계는 그 층을 지나는 **길을 늘릴 뿐 층을 뚫지 않는다**. 2단의 받기는 재진입 가드
  (`whileExtracting` — 해제 구간)와 `openSite(pinned)` 캡처를 승계하고, 직접 고르기의 열기는 레지스트리 확증과 같은 잣대
  (`decidePickedFolder`)를 지난다.
- **연결 없는 열기 금지**(§4.4 `link-consent` 취소 시): 무소속 폴더를 열어 전역 잔값이 유효
  사이트가 되는 창을 우리 제안이 만들지 않는다.
- 2단의 판 조회는 `captureTenant(picked)` 로 묶은 API 로 나간다 — 창의 유효 사이트(아직 x)가
  섞이지 않는다. 캡처 지점 수는 불변(기존 자리 승계, `check-capture-tenant` EXPECTED 2 유지).
- 새 문면의 보간(사이트 코드·경로)은 `say` 의 소독 정본을 지난다. QuickPick 는 명령 링크를
  렌더하지 않지만, 제어문자·초장문 차단은 알림과 같은 잣대로 받는다.
- 표식·링크를 쓸 때 만드는 부모 자리(`.zalkera`·`.vscode`)는 core `ensureOwnDir`(`safeWrite.ts`)
  이 **조각마다** 심링크·비폴더를 걸러 만든다 — 잎 심링크만 막는 `writeOwnFile` 은 부모가 링크면
  폴더 밖에 쓴다. 직접 고르기(§4.4)가 대화상자의 임의 폴더를, BYO 흐름이 git 레포(clone 이
  심링크를 실현한다)를 대상으로 하므로 「해제기는 심링크를 만들지 않는다」는 전제가 이 흐름에서
  성립하지 않는다. 링크를 만나면 조용히 고치지 않고 멈춰 말한다.

### 6.2 못 막는 것 (정직하게 적는다)

- **W2 오입양**은 남는다 — 표식 부재로 막지 않는 한 구조적이다. 방어선은 되돌림 단추(§4.6)와
  발행 확인 모달.
- **P? 에서의 다운로드 실패** — 조회가 실패한 채 다운로드를 누르면 오류로 끝난다. 모르는 것으로
  막지 않는 선택의 비용이고, 착지 문면(`noRevisionError`)이 정직하다.
- **멀티루트 창** — 첫 루트만 본다(정본 §2 기각의 귀결). 둘째 루트의 소속은 이 흐름이 모른다.
- 직접 고르기에서 사용자가 **의도적으로** 무소속 폴더를 y 에 연결하는 것 — 동의 모달을 지난
  사람의 결정이고, 서버 권한과 발행 모달이 최종 경계다(정본 §6.3 과 같은 판정).
- **P0 에서 받기 줄이 조회 왕복 동안 보인다** — 2단이 조회를 기다리지 않는 선택(§4.3)의
  비용이다. 그 창에서 누르면 `noRevisionError` 가 두 갈래로 정직하게 진단하고, 화면에는
  zip·직접 고르기가 같이 서 있다.
- **`ensureOwnDir` 의 확인·생성 사이 경합** — 확인과 `mkdir` 사이에 같은 기계의 다른 프로세스가
  심링크를 끼워 넣는 것까지는 막지 않는다. 같은 사용자 권한으로 동시에 움직이는 적대 프로세스는
  이 도구의 신뢰 경계 밖이다.
- **QuickPick 항목 라벨의 서버 값** — 1단 사이트 목록·프리셋·버전 목록은 서버가 정한 이름을
  라벨·설명에 그대로 싣는다. 명령 링크는 렌더되지 않지만 제어문자·초장문 잣대 밖이라 이름 위조
  표면이다. 이 판이 새로 낸 자리(2단·직접 고르기)는 리터럴 라벨과 `detail` 소독으로 닫았고,
  기존 자리는 별건으로 닫는다(§9 쟁점 7 — `check-notice.mjs` ⑷ 주석이 구멍으로 명시).

## 9. 미해결 쟁점 — 처분

1. **한 소스 → 여러 사이트 발행**(프랜차이즈·다지점) — **이연 유지(열림).** 재연결과 다른 동사
   (발행 대상의 복수화)로 판정했고 본 메모 범위 밖. 수요가 실물로 오면 별도 메모로 — 소속 모델
   (폴더 하나 = 사이트 하나)을 건드리는 설계라 이 흐름의 곁가지로 다루면 안 된다.
2. `fetchable: "unknown"` 에서 fetch 를 남기는 판정 — **닫힘(채택 확정).** 심의·구현이 그대로
   확정했다. 논블로킹 전환(§4.3) 뒤에는 조회 실패가 화면을 다시 그리지 않으므로, 「실패 단추를
   자주 낸다」던 우려의 형상도 P1 표면과 같아졌다.
3. 입양 토스트의 「다시 연결」 단추 상시 노출 — **닫힘(채택 확정).** 소음 신고가 실물로 오면
   §4.6 의 물러설 안(단추 없이 문면 한 줄)으로 — 새 사실 없이 재론하지 않는다.
4. 재등재 시점과 동일값 스킵 — **닫힘.** 활성화 1회(`onStartupFinished` — 임계 경로 밖) +
   동일값 스킵으로 확정, 갱신 경로 동승은 하지 않는다. 성능 축 심의가 표식 읽기 비용을 재고
   조치 불필요로 판정했다.
5. 원격(SSH) 창에서 레지스트리·경로가 같은 확장 호스트에 산다는 전제(§2.4) — **열림(판은 막지
   않는다).** 원격 창 확인은 미이행이다. 다만 전제가 틀려도 열기 제안은 확증(`confirmedFolderFor`
   — 실재 + 소속 일치)을 지나므로 다른 호스트의 경로는 걸러진다 — 실패의 형상이 교차 열기가
   아니라 **제안 누락**이다. 확인 방법: 원격 창 하나에서 받기 → 1단 `detail` → 2단 열기 왕복.
6. 1단 정렬 — **닫힘(기각 확정).** 정렬하지 않는다 — `detail` 의 「지금 작업 중」·확증 경로
   표시가 같은 정보를 이미 말하고, 서버 순서가 콘솔과 편집기에서 같게 유지된다. §4.8 은 삭제했다.
7. **QuickPick 항목 라벨 소독(신규·열림·별건).** 서버 값이 라벨·설명에 생으로 실리는 기존
   자리들(1단 사이트 목록·프리셋·버전 목록 — §6.2). 닫을 때 `createQuickPick` 의 `items` 간접
   대입까지 함께 본다 — `check-notice.mjs` ⑷ 주석이 구멍의 위치와 닫는 순서를 적어 뒀다.

## 10. 구현 심의 반영 (설계자 판정)

구현·검사기·3축 반영을 설계 대비로 심의한 판정이다. 3축이 이미 잡은 것은 재론하지 않는다.

| 대상 | 판정 | 처분 |
|---|---|---|
| §4.5 받기·zip 동일 판정 — zip 소비처(`importZipCommand`)가 `decideFetchTargetPlan` 을 안 지남 | **조건부 승인 → 이행됨** | **구현을 문서에 맞춘다.** 발단 신고의 ①이 「빈 폴더에 zip」이고, core 서명(판 번호 없는 입력)과 §8 ⑸(횟수 2)가 처음부터 두 소비처 형상이다. zip 은 `here` 갈래만 산다(§4.5) — `chooseImportTarget` 이 그 갈래만 두고 나머지는 대화상자로 간다 |
| §4.3 선조회를 논블로킹으로 | **승인** | §4.3 을 그 형상으로 개정. 조회를 앞세워 버는 것이 없고(시한을 넘기면 어차피 항목이 남는다) 흔한 칸의 즉시성을 산다. P0 노출 창은 §6.2 에 등재 |
| `FETCHABLE_PROBE_MS = 4_000` | **승인** | 낡은 답으로 화면을 다시 그리지 않는 선 — §4.3 에 등재. 상한이 없으면 항목이 한참 뒤에 손밑에서 빠지는 화면이 된다 |
| `fetchable` 의 `no-revision`/`no-ready` 분리와 승격 분리 | **승인** | §2.2 의 P0a/P0b 를 타입으로 세운 것. zip 승격을 P0a 로 한정한 것은 승격의 설계 근거(신규 테넌트 온보딩)를 자구보다 정확히 따른 것 — §4.1·§4.2 를 그 형상으로 개정 |
| §4.8 1단 정렬 미구현 | **기각 확정(문서에서 뺌)** | §9 쟁점 6 의 물러설 안 채택 — `detail` 표시만 남긴다. §4.8 삭제·§7 근거 정정·§8 행 삭제 |
| 심링크 부모(`ensureOwnDir`) | **승인** | 경계에서 정석으로 닫았다(조각별 확인·조용한 교정 없음). §6.1 에 등재, 남는 경합은 §6.2 |
| QuickPick 항목 라벨 기각(별건 처리) | **승인** | 이 판이 낸 표면은 리터럴 라벨로 닫혔고, 기존 자리를 이 판에 끌고 오면 근거가 위협이 아니라 검사기 출력에 놓인다. 추적은 §6.2·§9 쟁점 7 로 — 검사기 주석 하나에 맡기지 않는다 |
| 다중 사용자 덮어쓰기 축 | **별도 메모** | `DESIGN-concurrent-upload.md`. 본 메모의 「서버 계약 추가 없음」(§0·§7) 불변식과 층이 다르다 — 올리기 문과 원장 계약의 축이다 |

**이행 완료**(위 판정이 난 트랜치에서 함께 닫혔다):

1. zip 소비처의 `decideFetchTargetPlan` 배선과 §8 ⑸ 횟수 2 래칫.
2. 선조회 배선 — `check-wiring` 이 첫 그리기만 고정하고 조회(`probeFetchable`)와 다시 그리는
   줄은 안 세던 자리. 그 줄이 떨어지면 전건 초록인 채 P0 받기 항목이 상시로 되살아난다.
   두 줄 다 효과로 고정했다.

**잔여**:

3. §9 쟁점 5(원격 창 확인)·쟁점 7(항목 라벨 별건).

⚠ **받기 완료 문면의 넷째 갈래**(3회전 심의 산출). `into-open` 판정을 `findProjectRoot` 의
결과로 하면, 받은 꾸러미가 한 겹 감쌌을 때 루트가 한 단계 내려가 **고친 그 문장이 그대로 다시

있다는 사실과 「소스 폴더 열기」 단추를 함께 낸다(그 칸에서 단추를 없애면 갈 길이 사라진다).
